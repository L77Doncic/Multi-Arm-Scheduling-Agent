02 / Harness Engineering 框架

五个核心模块如何协作

Harness是系统的"大脑"，负责约束调度、异常处理和自我优化。

① TaskDecomposer 任务分解

输入：自然语言指令 + 场景配置
输出：结构化子任务列表 + 依赖DAG图
方式：LLM智能拆解 / 模板规则兜底
关键数据：operation_type, required_capabilities, dependencies, estimated_duration

→

② ResourceAllocator 资源分配

输入：任务列表 + 机械臂列表
输出：任务→机械臂映射表
算法：贪心评分 = 能力匹配(46%) + 负载均衡(23%) + 优先级(8%) + 并行机会(23%)
冲突检测：TEMPORAL(时间) / CAPABILITY(能力) / RESOURCE(资源) / COLLISION(碰撞)

↓

③ CodeGenerator 代码生成

输入：任务描述 + 场景参数 + 反馈数据
输出：可执行Python代码
原语：move_to, grip, release, rotate, linear_move, wait, check_sensor, set_payload, set_compliance
特点：动态组合，非固定模板

→

④ ResultValidator 结果验证

检查维度：
• 时间约束：任务是否在预期时间内完成
• 空间约束：机械臂是否碰撞
• 资源约束：是否超载
• 依赖约束：任务顺序是否正确
输出：is_valid + violations列表

↓

⑤ ExceptionHandler 异常处理

7种异常类型：TIMEOUT, RESOURCE_CONFLICT, COLLISION, COMMUNICATION_FAILURE, SIMULATION_ERROR, CODE_GENERATION_ERROR, CONSTRAINT_VIOLATION
4种恢复策略：RETRY(重试) / SKIP(跳过) / FALLBACK(降级) / REPLAN(重规划)
决策：根据异常类型+上下文自动选择恢复策略

→

⑥ FeedbackLoop 反馈闭环

分析：成功率、耗时分布、错误模式、瓶颈识别
调整6个参数：
• timeout_adjustment — 超时倍数
• retry_count — 重试次数
• resource_weight — 资源分配权重
• priority_boost — 优先级提升
• speed_factor — 代码生成速度系数
• force_factor — 抓取力系数
闭环：参数应用到ResourceAllocator/ExceptionHandler/CodeGenerator

03 / Harness Engineering 详解

ResourceAllocator 冲突检测与解决

4种冲突类型

类型含义示例
TEMPORAL时间冲突同一机械臂同时做两个任务
CAPABILITY能力不足机械臂没有"pick"能力
RESOURCE资源竞争两个任务争用同一工位
COLLISION碰撞风险两个机械臂路径交叉

分配算法流程

for each task: candidates = arms WHERE capability matches score = 0.46 × capability_match # 能力匹配 + 0.23 × workload_balance # 负载均衡 + 0.08 × task_priority # 任务优先级 + 0.23 × parallel_opportunity # 并行机会 assign task → highest_score arm # 并行机会：优先选择空闲臂 # 如果任务能与其他臂上的任务并行，给高分 # 冲突解决（迭代最多10轮） while conflicts exist: for each conflict: move lower_priority task → next_best arm

ExceptionHandler 决策树

exception = classify(error_msg) if exception.type == TIMEOUT: if attempts < max_retries: → RETRY (重试) else: → SKIP (跳过) if exception.type == COLLISION: → REPLAN (重规划，换路径) if exception.type == SIMULATION_ERROR: → FALLBACK (降级到模板代码) # 记录历史，用于统计分析 history.append(exception, recovery, outcome)

FeedbackLoop 参数调整规则

触发条件调整参数调整方式
成功率 < 80%timeout_adjustment×1.2（放宽超时）
成功率低retry_count+1（增加重试）
机械臂过载resource_weight+0.1（更均衡分配）
频繁失败priority_boost+0.1（提升优先级）
失败率 > 20%speed_factor×0.8（动作更慢更稳）
失败率 > 20%force_factor×1.15（抓得更紧）

06 / 实验数据分析

📊 数据分析与洞察

1. 引入MRTA旅行时间后，结果接近基准

平均Makespan比率：1.08x（非常接近MRTA基准）

说明加入移动时间后，我们的调度与MRTA最优解基本持平。

改进前（无移动时间）：0.07x~0.30x，严重低估实际耗时。改进后（含移动时间）：0.42x~1.67x，更接近真实场景。

2. 部分场景超过基准的原因

3p(1.18x)、4p(1.61x)、6p(1.67x) 长于MRTA基准

MRTA基准用MILP求解器找全局最优，我们用启发式规则。启发式方法在复杂场景下不够优化，但结果仍然可行。

3. 资源利用率仍需改进

平均资源利用率：35%

33% = 只有1台机器人在干活（1/3 ≈ 33.3%）

说明当前调度倾向于单臂串行执行，多臂并行调度能力不足。这是下一阶段优化的核心方向。

4. LLM接入后成功率94%

接入真实LLM API后，任务分解和代码生成质量提升

平均成功率：94%

LLM能更好地理解任务语义，生成更合理的调度方案。但仍有6%的失败率，需要进一步优化。

06 / 遇到的问题（仍然存在）

❌ 问题清单

严重 物理抓取不真实

工件通过"传送+冻结"附着到夹爪，不是物理仿真。FixedJoint在Isaac Sim pip包中API受限，无法实现真正的物理绑定。

严重 视频演示异常

视频中只拍到两个机械臂（应有三个），工件没有被夹取，机械臂运动轨迹混乱，画面不连贯。

严重 Isaac Sim进程崩溃

app.close() 调用 sys.exit() 导致SIGSEGV。每个实验必须用独立子进程+os._exit(0)。

环境 串流限制

Livestream Clients仅支持同局域网UDP传输。SSH只能转发TCP，无法传输UDP信号。Web流媒体需要Docker。

环境 Docker无法使用

①系统盘30G太小，无法同时装venv和Docker镜像；②autodl本身就是容器，嵌套Docker需要宿主机overlayfs挂载权限，容器内无法获得。

环境 环境损坏

conda升级破坏了miniconda3的Isaac Sim 6.0环境。simulation_app扩展丢失。4.5与6.0版本不兼容。

环境 磁盘空间不足

系统盘30G，Isaac Sim依赖(nvidia 4.1G + torch 1.7G)占大量空间，conda升级后只剩1.1G。

环境 网络受限

Docker Hub、阿里云、腾讯、网易镜像源均无法拉取。无法安装更新的Isaac Sim版本。

严重 视频黑帧/相机问题

Replicator帧捕获需render=True。相机位置过近导致机械臂在画面外。地面无Ground Plane导致工件穿透。

严重 资源利用率偏低

33%利用率意味着只有1台机器人在干活。多臂并行调度能力不足，是调度算法的设计问题。
